# 前端发布缓存与旧页面兼容说明

2026-10-11 支出台账发布后，已打开的浏览器仍运行旧版页面，点击新建或详情需要下载尚未加载的旧 JS 分包。新版镜像移除了这些分包，Nginx 又将不存在的 `/ext/app/assets/*.js` 返回为 SPA HTML（200、text/html），浏览器拒绝执行，页面跳转停住。截图中的“新建报账／主数据”及旧费用接口属于此前版本；服务器已经发布新版，问题出在发布兼容和缓存配置。

## 修复

- `/ext/app/` 的 HTML 及无版本引导文件返回 `Cache-Control: no-store`，刷新时读取当前入口。
- 带内容哈希的 `/ext/app/assets/` 返回长期 immutable 缓存；不存在的资源明确返回 404，不回退成 HTML。
- 前端镜像支持构建参数 `PREVIOUS_FRONTEND_IMAGE`，只继承此前版本的哈希资源，新版入口、路由文件及页面覆盖为本次构建。首次安装默认使用 Nginx 空目录；更新时必须传入当前生产前端镜像，以保留已经打开的页面所需分包。保留旧资源不恢复旧费用写入。
- 新版遇到 JS/CSS 加载失败，显示中文提示和“刷新页面”按钮，不自动刷新或循环重载，不主动丢弃未保存表单。

已经在浏览器中发生过模块加载失败的旧页面，需要一次强制刷新或重新打开菜单；服务端补回文件不会清除浏览器当前页面保存的失败模块状态。新版台账历史入口保留原单，不自动迁入或重算金额。

## 更新流程

记录当前生产前端镜像，构建新版时继承它：

```bash
docker build --build-arg PREVIOUS_FRONTEND_IMAGE=<当前前端镜像> \
  -t ops-extension-frontend:<新版本> frontend
```

仓库示例 Compose 也支持 `OPS_PREVIOUS_FRONTEND_IMAGE` 环境变量。线上使用独立生产 Compose 时，需要在发布覆盖配置中传入等价的 `build.args.PREVIOUS_FRONTEND_IMAGE`；切换仍只重建前端服务，使用 `--no-deps --no-build`，无需更新 Sub2API 或数据库。不要删除被继承镜像中的旧资源；若后续制定保留期限，应先确认旧会话已过期，并保留加载失败恢复提示。

本次首次修复需要同时保留发布前的旧报账版和本次台账版资源，后续新版继续继承当前镜像即可。旧资源只支持原页面读取和跳转，旧费用写入继续由后端默认拒绝。

`npm run test:release` 使用真实构建文件与 Chromium，仅提供合成 GET 数据，所有 API 写请求均被拒绝。已复现旧 iframe 请求缺失 JS 却收到 HTML 后无法跳转，并验证：

1. 保留原分包后，已打开的旧 iframe 能进入新建及原单详情。
2. 新版构建在 iframe 内能进入“记一笔”和详情，无页面错误。

## 菜单重新进入仍显示旧表单

后续截图仍显示“新建报账／保存草稿”，确认浏览器此前缓存的入口 HTML 尚未过期。新服务器响应增加 no-store 不会追溯清除已经存在的缓存；保留旧分包能恢复旧页面跳转，但不会将旧表单切换成新版。

登录引导 `/ext/auth/bootstrap` 在验证用户并创建会话后，为原目标 URL 增加每次不同的 `_ops_entry` 参数，避开旧入口缓存。参数不包含登录 token，保留原路径、其他查询参数和片段。Sub2API 中已配置的菜单 URL、菜单 ID、嵌入方式和权限保持不变，用户无需修改系统设置；从其他页面重新点击菜单即可取得新版入口。
