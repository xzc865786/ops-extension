# Ops Extension 线上 E2E 问题修复实施方案

依据：[2026-09-27 线上 E2E 测试报告](./线上E2E测试报告-2026-09-27.md)。本文件记录修复顺序与剩余验收。后续已在本地复现中文附件名引发的响应头编码异常，并完成相应代码修复；仍未取得服务器日志、MinIO 对象清单和原始上传失败请求，不能断言线上旧附件只有这一处原因。

**当前进度**：下载响应头与错误反馈、退出清屏、手机嵌入留白、中文展示、主数据必填反馈和文件选择器类型已在本地修改。后端测试、前端构建及类型检查通过；尚未部署和复测线上。下文的生产取证、上线与数据核对仍需执行。

## 目标与边界

- 修复已复现的旧工单附件下载错误、窄屏嵌入遮挡、独立页退出后保留旧数据，以及中文界面的枚举和时间展示问题。
- 对未复现的上传错误和历史付款异常先取证，再决定是否需要代码或数据修复。
- 保持现有四个 Sub2API 自定义菜单、Auth Bootstrap、业务 API 路径与现有附件访问权限。优先在 Ops Extension 内完成；不修改 Sub2API 源码。
- 目前预计无需数据库迁移或新增配置。若旧附件恢复需要移动对象或修正数据库记录，必须单独列出映射、备份、验证和回滚步骤后再执行。

## 实施顺序

| 阶段 | 工作 | 产出与进入下一阶段的条件 |
| --- | --- | --- |
| 1. 线上只读取证 | 定位旧附件下载实际失败点；核对原上传错误与付款异常 | 明确异常类型、对象是否存在、下载所走路径；保留脱敏证据，不改线上数据 |
| 2. 高优先级代码修复 | 下载错误处理、退出后清屏与跳转、手机嵌入布局 | 有针对性测试、前端构建和本地/测试环境页面复测 |
| 3. 展示与表单修复 | 分类和时间格式化、主数据必填反馈 | 列表、详情、报表一致回显；无 API 枚举变化 |
| 4. 回归与发布 | 测试环境集成、线上小范围复测、观察与回滚准备 | 报告中的失败项转为通过，未覆盖项明确记录 |

## 1. 旧工单附件下载（P1）

### 先定位，再选修复分支

1. 在生产环境只读检查工单 `T202609270002` 的附件 ID `1`：从后端日志按请求时间定位异常；记录 HTTP 状态、异常类型和调用点。不要记录 Cookie、签名 URL、存储密钥或完整请求头。
2. 核对 `ticket_attachments` 中该附件的 `object_key`、文件名、大小、SHA-256 与所属工单；在**当前实际配置**的 MinIO Bucket 中只读检查相同对象键及对象大小。对照本轮新上传且可下载的附件。检查实际部署使用的数据卷和历史迁移/恢复记录，不能仅凭仓库中的 Compose 文件推断线上卷名。
3. 查看下载响应链：`GET /ext/api/v1/attachments/1/download` 若返回重定向，继续检查浏览器可达的 MinIO 公网端点及签名 URL 目标；若由后端直接返回 500，除 `get_bytes` 和 MinIO 异常外，也核对已在本地复现的中文文件名响应头编码异常。现有实现根据公开端点配置在两条路径间选择。
4. 按证据处理：
   - **对象存在、访问配置错误**：修正实际端点、Bucket、权限或签名配置；对新旧附件分别复测。配置变更单独记录并安排回滚。
   - **对象缺失但有可信备份**：先备份当前数据库和对象存储，再按原 `object_key` 恢复对象；核对大小和 SHA-256，确认附件权限及下载正常。不得用同名但内容不明的文件替换。
   - **对象确实无法恢复**：保留附件及审计记录，向用户显示明确的“附件文件不可用”提示，并提供受控重新上传途径；不要伪造文件或静默修改旧记录。

### 代码处理

在 [附件下载路由](../backend/app/attachments/router.py)及[MinIO 客户端](../backend/app/attachments/minio_client.py)中，对已授权请求区分“记录不存在”“对象不存在”“存储服务暂不可用”。对象缺失返回可识别的 404（如 `ATTACHMENT_OBJECT_MISSING`）；连接、权限或签名服务故障保留服务端错误语义并记录附件 ID、来源类型及异常类别，响应中不泄露内部端点或凭据。签名跳转路径也要覆盖目标对象缺失的诊断，避免只测试默认代理路径。前端附件入口应能显示失败提示，而不是留下仅有 `Internal Server Error` 的空白标签页；若下载方式改为受控请求，仍须兼顾大文件、文件名和浏览器下载行为。

**验收**：旧附件若可恢复，成功下载且哈希一致；若不可恢复，页面出现明确提示。新上传的 TXT/PDF/PNG 和报账附件继续下载成功；无权限用户仍收到 403；对象缺失、存储故障、代理下载与签名跳转各有针对性测试。不得把所有存储异常统一伪装成 404。

## 2. 上传错误取证（当前未复现）

现有上传逻辑在[工单路由](../backend/app/tickets/router.py)读取文件后交给[附件校验与存储](../backend/app/attachments/minio_client.py)；已关闭工单会拒绝上传，允许类型和大小受校验。前次线上报告缺少失败请求证据，本轮小文件 TXT/PDF/PNG 均成功，因此暂不改上传业务规则。

1. 收集失败时的工单号与状态、用户角色、文件扩展名和大小、浏览器显示文案、请求状态码与响应错误代码、后端同一时刻日志。文件内容若含隐私，不要求提供原件；可以用同类型同大小的无敏感样本复现。
2. 在测试环境覆盖用户与管理员入口、允许/不允许类型、0 字节、接近与超过 20MB、关闭工单、MinIO 暂不可用，并核对失败反馈是否对应后端错误。
3. 只有复现出产品缺陷后才修改：例如前端没有展示后端错误则补充反馈；浏览器 MIME 与扩展名处理不一致则按具体失败样本修正；存储故障则修复对应配置或故障处理。文件大小和类型策略如需改变，应另行确认产品要求。

**验收**：原失败条件可稳定复现并在修复后通过；若仍无法复现，记录证据缺口和已覆盖矩阵，不声称“上传已修复”。

## 3. 手机嵌入页被宿主浮层遮挡（P2）

在[全局样式](../frontend/src/style.css)的嵌入模式窄屏断点下，为宿主位于 iframe 右上角的“新窗口打开”浮层预留顶部空间，确保首行按钮及工单页签从浮层下方开始。统一处理所有嵌入页，独立打开和桌面宽度维持当前布局。优先以小范围、可复用的容器规则实现，避免各页面分别塞入固定空白；只保留表格容器横向滚动。

**验收**：在真实 Sub2API 自定义菜单中检查 320、390、768px 及桌面宽度，逐一验证“新建报账”“主数据”“新建工单”、工单管理状态页签和报表查询/导出按钮可见且可点击；无横向页面溢出、重复导航或双层纵向滚动。浅色和深色各检查一次。

## 4. 退出后仍显示旧业务数据（P2）

当前[认证 Store](../frontend/src/stores/auth.ts)退出时清空 `me`，但[页面外壳](../frontend/src/App.vue)仍渲染原路由，已加载的表格留在内存中。退出按钮应在清除会话后立即卸载受保护业务页面，并用 `router.replace` 进入现有[未授权页](../frontend/src/views/auth/AuthError.vue)。请求失败时也不能继续展示已加载数据；避免未完成的异步加载在退出后重新写回可见页面。必要时在[路由守卫](../frontend/src/router/index.ts)统一拦截已失效会话。

**验收**：点击退出后当帧不再显示工单、报账或报表数据；浏览器后退和刷新均不能恢复旧内容；重新通过 Sub2API 菜单 Bootstrap 后可正常进入。独立页退出与宿主会话重新进入的关系需按现有设计验证，不改变 Sub2API 登录状态。

## 5. 中文标签、时间与主数据校验（P3）

- 分类展示：现有 `/tickets/meta` 和 `/admin/expenses/meta` 已提供分类的 `value/label`，优先在前端复用并封装统一展示函数；覆盖[我的工单列表](../frontend/src/views/tickets/TicketList.vue)、工单详情、[报账列表](../frontend/src/views/admin/expenses/ExpenseList.vue)、报账详情和[报表“按分类”](../frontend/src/views/admin/reports/ReportDashboard.vue)。未知枚举值保留原值，避免空白。提交和筛选仍传原枚举值；CSV/Excel 导出字段暂不改变。
- 时间展示：建立统一的日期时间格式化函数，明确使用浏览器本地时区和 `zh-CN` 展示；覆盖工单列表、详情消息与事件时间。对空值或无效时间安全回退，不改变 API 时间戳和存储时区。
- 表单提示：在[主数据页面](../frontend/src/views/admin/expenses/Masters.vue)给供应商名称、成本中心 CODE/名称、付款账户必填字段做提交前检查与可见提示，同时保留后端验证和错误提示。不要在空字段时静默返回；成功后清除错误。

**验收**：上述页面显示“其他”“云服务器”等中文名称，时间按测试浏览器时区正确转换；空值提交能指出必填字段，合法数据仍可创建和启停。前端构建通过；列表、详情、报表互相一致。

## 6. 历史付款异常与未覆盖项

- 对报账 `E202609270001` 的异常先做只读核对：单据金额、付款流水、状态事件、报表排除逻辑和迁移记录。形成“数据录入问题 / 迁移问题 / 计算问题”的证据结论。任何修改付款流水或重算金额的方案须单独列出旧值、新值、审批人、备份与回滚；本轮代码修复不顺手改财务数据。
- 主题联动尚未实测浅色切换。发布验收时由宿主侧栏分别设置浅色、深色、跟随系统并重新进入四个菜单，核对 Bootstrap 传入的 `theme`、`ops_theme` Cookie 与[首次绘制主题脚本](../frontend/public/theme-init.js)的实际显示。只有发现不一致时才增加主题修复任务。
- 非管理员账号的附件访问、内部备注不可见性需要真实普通账号或测试环境账号验证。审批通过、登记付款应在隔离的测试环境用专用数据完成，不用生产真实财务单据补测。

## 验证、发布与回滚

1. 为附件错误分支补充后端测试：`backend/tests/test_auth_and_attachments.py`，必要时补 MinIO 集成测试；退出、窄屏和中文展示以实际页面交互回归为主。运行仓库现有后端测试（`PYTHONPATH=. pytest -q`，在 `backend` 目录）及前端 `npm run build`，记录实际结果。没有覆盖到的场景不能写“全部通过”。
2. 测试环境按报告操作复跑：四个菜单、附件新旧下载、上传边界、退出/后退、390px 操作、浅深主题、CSV/Excel；保留请求状态、截图和文件哈希。财务审批与付款仅在隔离环境执行。
3. 上线前保存当前应用镜像/版本，确认数据库与 MinIO 备份可恢复；先发布不涉及数据修复的代码，复测关键路径并观察后端存储错误。若需要恢复旧对象，单独执行已核准的数据恢复步骤并复核哈希。
4. 代码回滚使用上一版应用镜像/提交，并恢复对应配置；对象或数据库变更按事前备份和逐项映射回滚。不要使用删除整个 MinIO 卷或重置数据库的方式回滚。

**完成判据**：P1 的旧附件结果有可验证的恢复或明确不可恢复结论，用户看到可理解的反馈；P2 两项线上复测通过；P3 展示与必填提示一致；上传问题和付款异常各有证据结论，未验证项明确留在验收记录中。
