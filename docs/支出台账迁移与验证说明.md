# 支出台账迁移与验证说明

本次实现按《支出记录与月度开支简化实施计划》的产品规则执行。验证日期：2026-10-11（北京时间）。实现及隔离验收阶段未接触生产财务数据；随后经用户明确授权提交、推送并发布生产，实际记录见文末。

## 数据与金额规则

- 新建默认需要报销，保存立即记账，无提交或审批步骤。付款人初始为空、自由填写、去除首尾空格后精确匹配；创建人和操作人单独记录。
- CNY 的人民币金额等于原金额。USD 的自动换算使用后端保存的参考快照，服务端 Decimal 按 ROUND_HALF_UP 舍入到分。手填结果保留参考快照，无报价时记为人工填写，不伪造汇率。
- 参考汇率查询采用固定 Frankfurter v2 USD/CNY 地址、5 秒超时、最多 30 分钟缓存。显式刷新失败返回失败；有效日期及实际获取时间保留。已保存账目不参与缓存刷新或重估，编辑初始化也不请求新汇率。
- 支出日期决定月份，年付全额计入该月。报销只偿还垫款，不增加费用，也不移动费用所属月份。
- 一批只允许同一付款人的有效待报销记录，支持混合 CNY/USD。总额不同须填写差额说明，仍表示整批结清。采用整数分和最大余数法分配，余数相同时按记录 ID 排序；逐笔实际金额非负，合计等于实报总额。
- 已报销核心字段更正前须撤销整个批次，原批次、逐笔明细、凭证和操作事件保留。非金额编辑保留完整已保存换算快照。

## 数据库迁移

迁移 head 从 `007` 追加至 `008`，没有修改既有 revision。新增六张表：

| 表 | 用途与约束 |
| --- | --- |
| `expense_rate_quotes` | 持久化参考汇率引用，12 位小数、有效日期、带时区获取时间和来源 |
| `expense_records` | 原币、人民币记账额、模式和汇率快照、自由文本付款人、创建/修改操作人、版本号、有效性；创建幂等键唯一，旧单据关联可空且唯一 |
| `expense_reimbursements` | 整批人民币实报额、报销日期、差额说明、登记人和撤销信息；幂等键唯一 |
| `expense_reimbursement_items` | 逐笔应报销快照、实报分配及差额；有效关联列唯一，撤销后置空，历史明细保留 |
| `expense_ledger_attachments` | 支出凭证或批次凭证，数据库约束要求恰好归属于其中一种；存储元信息沿用原实现 |
| `expense_ledger_events` | 创建、编辑、作废、报销、撤销、上传及历史确认的前后值、操作人名称/编号与时间 |

金额列为 Numeric(18,2)，汇率列为 Numeric(24,12)；新增模型沿用 BigInt/SQLite 类型适配。支出及报销日期为 Date，事件和获取时间为带时区 DateTime。索引覆盖支出日期、付款人、明细和事件查询。

原审批单、数量明细、税务、同币种付款流水、附件、事件和历史主数据均保留。迁移没有批量转换金额、填充付款人或建立伪报销。

`008` 的 downgrade 有保护：新财务表有记录时拒绝删表；空表才允许退回 `007`。应用回滚不应执行数据库 downgrade。

## API 与兼容性

| 能力 | 新接口（均为管理员权限） |
| --- | --- |
| 分页及筛选 | `GET /ext/api/v1/admin/expense-records`；`page/page_size/month/payer/category/status/keyword/mine/voided`，空 `month` 表示全部月份，省略表示本月 |
| 录入及详情 | `POST /expense-records`、`GET/PATCH /expense-records/{id}`（以下省略公共管理员前缀） |
| 作废 | `POST /expense-records/{id}/void`，需版本与原因 |
| 常用信息及参考报价 | `GET /expense-records/meta`、`GET /expense-records/rate?refresh=true` |
| 报销 | `POST /reimbursements/preview`、`POST /reimbursements`、`GET /reimbursements/{id}`、`POST /reimbursements/{id}/revoke` |
| 月报及完整 Excel | `GET /expense-records/monthly`、`GET /expense-records/export`，共享查询及统计逻辑 |
| 历史盘点及确认 | `GET /expense-records/history`、`POST /expense-records/history/{claim_id}/confirm` |
| 凭证上传 | `POST /expense-records/{id}/attachments`、`POST /reimbursements/{id}/attachments` |

前后端以十进制字符串传递金额。创建及报销需 `idempotency_key`；同键同内容返回原结果，不同内容返回冲突。更新使用完整录入字段加 `version`，作废及撤销使用 `version/reason`。旧版本或并发竞争返回明确 409 提示，报销重新验证锁定记录的状态、付款人、版本和金额，整批事务提交。

附件下载继续用原下载 API，新增明确来源 `source=expense-record` 和 `source=reimbursement`；旧 `expense` 和 `ticket` 保留。来源不匹配返回 404，未知来源返回 400，不用数字 ID 猜测所属表。工单权限和正常下载行为不变。普通 Excel 不携带内部存储地址或附件签名链接。

以下属于兼容性变化：

- 默认旧 `/admin/expenses` 及旧供应商、成本中心、付款账户的写接口返回 409 `LEGACY_EXPENSE_READ_ONLY`，提示使用新版支出记录。历史读取和旧附件保持可用。原写接口请求结构未被改造成新版语义。
- 旧 `/admin/reports/*` 保留旧币种/审批口径，响应及导出带 `X-Report-Scope: legacy-claims-original-currency`；不能把其结果作为新版人民币月报。新月报使用独立接口。
- 前端 `/admin/expenses`、新建/编辑/详情及 `/admin/reports` 路径保持不变；Sub2API 的原 bootstrap 链接保持不变，只更新菜单名称。新增历史次级入口 `/admin/expenses/history`，日常导航移除主数据。
- 环境变量新增 `LEGACY_EXPENSE_WRITES_ENABLED`，默认 `false`，Compose 已传入。它只供明确的旧流程回退使用；恢复旧写入不会使旧单自动计入新统计。
- 后端容器启动不再自动运行 `seed_defaults`，避免覆盖历史主数据，也无需种子才能记账。原种子工具保留供旧流程显式维护。
- 没有增加 Python/npm 运行依赖，也没有新增付费服务或 API key 要求。新增前端专项命令 `npm run test:expenses`。

## 历史资料核对

“支出记录 → 历史单据”列出原状态、币种、金额、付款异常、附件数量及是否已迁入。迁入必须人工确认购买内容、日期、付款人、有效新币种金额及报销情况。旧 USD 不自动取今天汇率；旧申请人不自动当作付款人；旧已付款不自动认定为报销。已确认有金额、日期依据的历史报销才创建独立批次。

旧 CNY 可预填金额；其他币种、零金额、部分/跨币种付款及取消状态继续保留原始资料，补齐有效新台账信息后才能确认。原单关联有唯一约束，重复确认不重复记账。关联的旧附件直接按原归属下载，无需复制存储文件。

未迁入原单不进入新人民币总额。列表、月报与 Excel 都显示“历史未核对记录未计入”及数量。

只读盘点命令（先确认目标库，输出包含财务资料，请妥善保存）：

```powershell
# backend 目录，使用项目 Python 环境；迁移到 008 后使用
python -m scripts.inventory_expenses --output expense-history-inventory.json
```

PostgreSQL 盘点事务设置为 READ ONLY。隔离验收在一次性测试库盘点两张人工构造原单：USD 已付但无付款流水，以及 HKD 零金额已取消。输出均保留，待确认数为 2，没有产生新台账记录。样本输出见 `output/ledger-validation/history-inventory.json`。授权发布时另行完成生产只读盘点，真实财务输出仅保存在服务器受限备份目录，不提交仓库。

## 发布前准备与回退

以下是发布和回退操作要求；本次授权发布的实际执行结果见文末。

1. 安排维护窗口，暂停新旧费用写入，保存当前后端/前端镜像与配置。备份数据库（例如 `pg_dump --format=custom --file=ops-before-ledger.dump`，通过受控连接参数连接目标库），备份/保留对象存储，并在隔离库验证备份可恢复。
2. 在备份恢复出的隔离 PostgreSQL 上运行 `alembic upgrade head`，应到 `008`。运行只读盘点，记录待核对和异常清单。无需运行旧修正工具或清空业务数据脚本。
3. 同步准备新版后端与前端，保持 `LEGACY_EXPENSE_WRITES_ENABLED=false`。部署前在实际服务网络检查参考报价可达性，及真实 Sub2API 管理员/普通用户、浅深主题与 Cookie/Bootstrap 行为。
4. 用户决定发布后才切换应用。旧浏览器写请求将收到明确冲突提示，不能继续生成不进入新报表的数据。逐单人工确认旧资料，核对原始凭证后再迁入，不自动批量推断。

回退时先在网关暂停新旧财务写请求，备份回退时点的完整数据库并导出新台账、报销明细及盘点清单。保留所有 `008` 新表及对象存储文件，恢复旧应用镜像和前端；旧应用无法展示新台账，须保留新版只读环境或备份供审计与重新切回使用。是否恢复旧写入应由负责人明确决定，记录切换时点与新增旧单清单，避免新旧重复记账。若仍运行新版后端兼容旧前端，可显式设置回退开关为 `true`；再次切回新版时关闭该开关并重新盘点。

禁止用 `rollback_all_data`、清表、无数据核对的 downgrade，或恢复较早备份覆盖已经产生的新账。空库 downgrade 已演练，有新记录的降级拒绝也已演练；含新财务数据的应用回退需保留数据，无自动删除路径。
