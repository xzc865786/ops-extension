# 工单分类表单与 Sub2API 订单对接实施方案

> 状态：方案已确认，三期均已实施：一期表单配置化（迁移 `005`）、二期订单校验（迁移 `006`）、三期退款与开票处理（迁移 `007`）。
> 依据：Ops 当前 `main`（f01e917）的工单实现；Sub2API `v0.2.13` 源码（Wei-Shaw/sub2api）。

## 0. 已确认的决策

| # | 问题 | 决策 |
|---|---|---|
| 1 | 字段定义放哪里 | **后台可配置**，按版本保存，可以回滚 |
| 2 | 退款规则 | 允许部分退款，**最终金额由管理员审核时确定** |
| 3 | 开票 | 只开电子普通发票，不开专票；管理员在税务平台开票时手动发到用户的收票邮箱，Ops 只登记 |
| 4 | 模块归属 | 退款、开票继续放在工单里 |
| 5 | Sub2API | 要对接：订单查询和校验，并在工单里直接执行原路退款 |
| 6 | 退款成功后 | 自动把工单改为已解决，并自动回复用户 |
| 7 | 扣减余额 | 默认开启，管理员可以关闭，关闭时显示警告 |
| 8 | 开票订单数 | 一张开票工单最多 10 个订单 |

## 1. 目标

1. 每个工单分类有自己的表单字段、必填规则和提示文字，管理员在后台修改，不用发版。
2. 退款、开票、充值类工单提交时校验订单号：订单必须存在，并且属于当前用户。同一订单不能重复申请退款或开票。
3. 管理员在工单详情页审核后，可以直接通过 Sub2API 原路退款。实退金额、扣减的余额和操作人全部记录在工单上。
4. 开票工单有结构化的处理结果：发票号、开票日期、开票金额、发票 PDF。
5. 历史工单照常显示，不丢数据。

## 2. Sub2API 对接核对结果（v0.2.13）

### 2.1 可用接口

所有管理端接口都用请求头 `x-api-key: <Admin API Key>` 鉴权，见 `backend/internal/server/middleware/admin_auth.go`。

| 用途 | 接口 | 说明 |
|---|---|---|
| 按订单号查订单 | `GET /api/v1/admin/payment/orders?keyword=&user_id=&page_size=` | `keyword` 对 `out_trade_no`、邮箱、用户名做**模糊**匹配，Ops 拿到结果后再按订单号精确比对 |
| 订单详情 | `GET /api/v1/admin/payment/orders/:id` | 返回 `amount`（到账额度）、`pay_amount`（实付）、`bonus_amount`、`currency`、`status`、`order_type`、`refund_amount`、`user_id` 等字段 |
| 执行退款 | `POST /api/v1/admin/payment/orders/:id/refund` | 请求体 `{amount, reason, force, deduct_balance}` |
| 查询并确认退款结果 | `POST /api/v1/admin/payment/orders/:id/refund/query` | 用于网关异步返回、订单处于 `REFUND_PENDING` 的情况 |

用户在 Sub2API“我的订单”页看到的订单号是 `out_trade_no`。工单表单里的“订单号”就填这个值。

### 2.2 必须遵守的退款规则

这些都是 Sub2API 的硬限制，Ops 界面要明确告知管理员。

- **每个订单只能退款一次。** 只有 `COMPLETED / REFUND_REQUESTED / REFUND_PENDING / REFUND_FAILED` 状态的订单可以退款。部分退款后订单变成 `PARTIALLY_REFUNDED`，**之后不能再退**。所以部分退款就是这个订单的最终结果，管理员确认前要看清楚。
- **退款金额以“到账额度”为单位**，不能超过 `amount`。原路退回的实付金额按 `pay_amount × 退款金额 ÷ amount` 折算，全额退款时退回全部 `pay_amount`。面板上要把两个数字都显示出来。
- **`amount` 不传或传 0 表示全额退款。** Ops 必须始终传明确的金额，防止误操作变成全额退款。
- **`deduct_balance=true` 时扣减用户余额。** 余额不足时，Sub2API 返回 `require_force=true` 和提示，不执行退款；带上 `force=true` 重新请求后，只扣减用户现有的余额。
- **订阅类订单扣减全部订阅天数。** 订单类型为订阅时，开启扣减会扣掉这笔订单的全部订阅天数（天数不够时直接撤销订阅），**和退款金额无关**。
- **赠送额度（`bonus_amount`）不会自动扣回。** 管理员需要在面板上看到这个数字，自行决定如何处理。
- **用 Admin API Key 发起的操作，在 Sub2API 审计日志里都记在“第一个管理员”名下。** 所以真正的操作人只能靠 Ops 自己记录。

### 2.3 上线前在 Sub2API 后台要完成的准备

1. 系统设置 → 生成 **Admin API Key**，配置到 Ops 服务器的 `.env`，不要提交进仓库。
2. 确认第一个管理员账号已完成“管理员合规确认”。否则管理端支付接口会返回 `423 ADMIN_COMPLIANCE_ACK_REQUIRED`。
3. 支付服务商实例开启 **允许退款**，关闭 **允许用户申请退款**，让用户统一通过工单申请。

### 2.4 安全风险

Admin API Key 拥有 Sub2API 的**全部管理权限**，v0.2.13 不支持限定权限范围。应对措施：

- Key 只存在后端环境变量里，不写进数据库，不返回给前端，不写入日志，错误信息里也会脱敏。
- Ops 的 Sub2API 客户端只开放上表 4 个接口，代码里写死白名单，不提供通用转发。
- Key 没配置时，订单查询和自动退款自动关闭，回退到手动登记，工单功能照常可用。

## 3. 总体设计

```
管理员 ──► 表单配置中心（带版本） ──► /tickets/meta ──► 用户端按配置渲染表单
                                                      │
用户提交 ──► 按配置校验 ──► 订单分类：查 Sub2API 校验归属 ──► 生成工单 + 订单快照
                                                      │
管理员审核 ──► 退款面板 ──► Sub2API 执行退款 ──► 记录操作 + 写事件 + 自动回复
            └► 开票面板 ──► 登记发票号 + 上传 PDF ──► 用户可下载
```

### 3.1 配置结构

配置按版本保存，存储方式和手册配置中心一致：带版本号、并发保存时检查版本、可以回滚。第一次使用时，用仓库里的默认配置 `backend/app/tickets/default_form_config.json` 生成第 1 版。

```jsonc
{
  "categories": [
    {
      "key": "REFUND",                 // 存进 tickets.category，创建后不能修改
      "label": "退款",
      "description": "已充值未使用的额度申请原路退回",
      "kind": "refund",                // general | refund | invoice | payment，决定业务行为
      "enabled": true,
      "notice": "已消耗的额度不予退还；最终退款金额以客服审核为准。",
      "title_mode": "auto",            // required | optional | auto
      "title_template": "退款申请 · {order_no}",
      "description_mode": "required",  // required | optional | hidden
      "attachment_hint": "",
      "require_attachment": false,
      "fields": [
        { "key": "order_no", "label": "订单号", "type": "order_no", "required": true, "system": true,
          "help": "在 Sub2API「我的订单」中复制订单号" },
        { "key": "expected_amount", "label": "期望退款金额", "type": "money", "required": false,
          "help": "留空表示由客服核定" },
        { "key": "reason", "label": "退款原因", "type": "select", "required": true,
          "options": [{ "value": "NOT_NEEDED", "label": "不再需要" }, { "value": "QUALITY", "label": "服务质量问题" },
                      { "value": "MISTAKE", "label": "误充值" }, { "value": "OTHER", "label": "其他" }] },
        { "key": "policy_ack", "label": "我已了解：已消耗额度不退，退款后扣减对应余额", "type": "confirm",
          "required": true, "system": true }
      ]
    }
  ]
}
```

**字段类型白名单**

| 类型 | 说明 |
|---|---|
| `text` / `textarea` | 文本，上限分别为 500 和 5000 字 |
| `number` / `money` | 数字和金额，金额最多两位小数且大于 0 |
| `select` / `radio` | 单选，值必须在选项里 |
| `confirm` | 勾选确认，必填时必须勾选 |
| `date` / `datetime` | 日期和时间 |
| `email` | 邮箱 |
| `order_no` | 单个订单号，提交时查 Sub2API |
| `order_no_list` | 多个订单号，最多 10 个，用于开票 |

所有字段都支持 `required`（必填）、`help`（提示）、`placeholder`（占位文字）、`max_length`（长度上限）和 `show_if`（显示条件）。`show_if` 的格式是 `{field, equals | in}`，只能引用同一分类里排在前面的字段。

**配置保存时的校验规则**

- 分类 key 符合 `^[A-Z][A-Z0-9_]{1,39}$`；分类内字段 key 符合 `^[a-z][a-z0-9_]{0,39}$`，并且不能重复。
- 已有工单使用的分类不能删除，只能停用。现有 11 个分类作为内置分类，只能停用。
- 标了 `system: true` 的字段，管理员可以改文字说明，但不能删除，也不能改类型和必填。各业务类型的系统字段：
  - `refund`：`order_no`、`policy_ack`
  - `invoice`：`order_nos`、`title_type`、`title`、`tax_id`、`email`
  - `payment`：`order_no`
- `show_if` 不能引用不存在的字段，也不能引用排在后面的字段。
- 所有文字说明一律按纯文本显示（不用 `v-html`），可以换行。

### 3.2 数据模型（迁移 `005_ticket_forms.py`）

| 变更 | 内容 |
|---|---|
| 新表 `ticket_form_config_versions` | 字段和 `manual_config_versions` 相同：version、config、note、restored_from、created_by_* |
| `tickets` 新增字段 | `form_version INT`、`form_schema JSONB`（提交时这个分类的字段定义快照）、`form_data JSONB NOT NULL DEFAULT '{}'`、`resolution JSONB`（管理员处理结果） |
| 新表 `ticket_orders` | `ticket_id`、`purpose`（REFUND / INVOICE / PAYMENT）、`out_trade_no`、`sub2api_order_id`、`snapshot JSONB`（提交时的金额、状态、类型、支付时间）、`created_at`；`out_trade_no` 和 `(sub2api_order_id, purpose)` 建索引 |
| 新表 `ticket_refund_operations` | 每次退款请求记一行：`ticket_id`、`sub2api_order_id`、`amount`、`deduct_balance`、`force`、`operator_user_id`、`operator_name`、`result`（SUCCESS / PENDING / REQUIRE_FORCE / FAILED）、`response_summary JSONB`、`created_at` |
| `ticket_attachments` 新增字段 | `kind VARCHAR(20) DEFAULT 'GENERAL'`，可选值 GENERAL / INVOICE_FILE |
| 历史数据回填 | 把旧工单的 `request_id / model_name / api_endpoint / occurred_at / error_message` 写入 `form_data`，`form_schema` 按默认配置生成。原有的 4 列这次保留不删，下个版本再清理 |

**为什么存字段快照（`form_schema`）**：管理员以后改了字段说明、删了字段，或者改了工单分类，老工单仍然按提交时的字段定义显示，不会出现找不到标签的空白字段。

`category` 字段不再用代码里的 `TicketCategory` 枚举校验，改为按当前配置校验：分类必须存在且已启用。管理员修改分类时，允许改成已停用的分类。

需要同步更新 `backend/scripts/rollback_all_data.py`，把新增的 3 张表加进清理范围。

### 3.3 后端接口

**用户端**

| 接口 | 变化 |
|---|---|
| `GET /tickets/meta` | 返回已启用分类的完整字段定义和当前配置版本号 |
| `GET /tickets/orders/lookup?out_trade_no=` | **新增**，查询前预览订单。只返回属于当前用户的订单；订单不存在和不属于本人返回同一个提示“未找到该订单”。按用户限流（每分钟 20 次），防止枚举订单号 |
| `POST /tickets` | 请求体新增 `form_data` 和 `form_version`。后端按当前配置校验，隐藏字段的值丢弃，不认识的字段拒绝。配置版本已经变了时，返回 `FORM_CONFIG_CHANGED`，前端提示用户刷新 |

**提交订单类工单时的校验**（Sub2API 未配置时跳过，只校验订单号格式）：

1. 订单存在，且 `user_id == 当前用户的 sub2api_user_id`。
2. 退款：订单状态必须是 `COMPLETED` 或 `REFUND_FAILED`；同一订单如果已有未关闭的退款工单，拒绝并提示已有的工单号。
3. 开票：订单状态必须是 `COMPLETED` 或 `PARTIALLY_REFUNDED`；同一订单如果已有未关闭的开票工单，或者已经开过票，拒绝。可开票金额 = Σ(`pay_amount` − 已退金额折算成的实付金额)，**由系统计算**，用户不用填。
4. 校验通过后，把订单快照写入 `ticket_orders`，标题按模板自动生成。

**管理端**

| 接口 | 说明 |
|---|---|
| `GET/PUT /admin/tickets/form-config`、`GET /versions`、`POST /versions/{v}/restore` | 表单配置中心，用法和手册配置中心一致 |
| `GET /admin/tickets/{id}/orders/live` | 从 Sub2API 实时拉取关联订单的当前状态 |
| `POST /admin/tickets/{id}/refund` | 请求体 `{amount, deduct_balance, force, reason}`，见 3.4 |
| `POST /admin/tickets/{id}/refund/query` | 查询处于 PENDING 的退款结果 |
| `PUT /admin/tickets/{id}/resolution` | 登记处理结果：驳回、手动登记退款、开票信息 |
| `GET /admin/tickets?keyword=` | 关键词搜索同时匹配 `ticket_orders.out_trade_no` |

### 3.4 退款执行流程

1. 管理员打开退款工单，面板显示 Sub2API 实时订单信息：到账额度、实付金额、赠送额度、订单类型、当前状态、已退金额，以及用户填的期望金额和原因。
2. 管理员填写**实际退款金额**（默认是用户的期望金额，没填则为订单全额），选择是否扣减余额（默认开启，关闭时显示警告）。面板实时显示“原路退回 ¥X（按实付折算）”。
3. 二次确认弹窗写明：退回金额、扣减余额、订单类型是订阅时扣减全部天数、**部分退款后这个订单不能再退**。
4. 后端执行：
   - 锁住工单行，防止重复点击并发提交；检查没有正在进行的退款操作。
   - 先写一条退款操作记录，再调用 Sub2API。退款原因统一写成 `工单 T2026xxxx · 操作人 xxx · <管理员填写的原因>`，这样在 Sub2API 后台也能追溯到工单。
   - 按返回结果处理：

| Sub2API 返回 | Ops 处理 |
|---|---|
| `success=true` | 记录为 SUCCESS，写入 `resolution`（实退金额、扣减余额或天数、时间、操作人），添加退款成功事件。按模板自动回复用户“已原路退回 ¥X，预计 1–3 个工作日到账”，工单状态改为 **RESOLVED** |
| `require_force=true` | 记录为 REQUIRE_FORCE，把提示（比如余额不足）展示给管理员。管理员再次确认后，带 `force=true` 重新提交 |
| 订单变为 `REFUND_PENDING` | 记录为 PENDING，面板显示“退款处理中”和“查询结果”按钮 |
| 网关失败 / 4xx / 5xx | 记录为 FAILED，显示脱敏后的错误信息。订单状态变成 `REFUND_FAILED` 后可以重试 |

5. **驳回**：管理员填写驳回原因，原因作为回复发给用户，`resolution.outcome=REJECTED`，然后可以把工单改为已解决或关闭。
6. **手动登记**：Sub2API 没配置，或者管理员在 Sub2API 后台直接退了款时，点“同步订单状态”，从订单的 `refund_amount` 回填处理结果；Sub2API 没配置时手动填写。

**状态约束**：退款类工单要改为 RESOLVED，`resolution` 必须是 REFUNDED 或 REJECTED。已经执行过退款的工单，不能再改成别的分类。

### 3.5 开票处理流程

1. 面板显示：开票订单、系统算出的可开票金额、抬头类型、抬头名称、税号、收票邮箱。
2. 管理员在税务平台开票，系统外操作。电子发票通常由平台直接发到收票邮箱。
3. 回到 Ops 登记发票号码、开票日期、开票金额（不能超过可开票金额），**上传发票 PDF**（附件类型为 INVOICE_FILE，用户在工单里也能下载），勾选“已发送至 收票邮箱”。
4. 系统自动回复用户，工单改为 RESOLVED。开票类工单不登记发票信息就不能改为已解决（驳回除外）。
5. **这次不做**：Ops 自己发邮件（目前没有邮件服务），开票后再退款的红冲提醒。

## 7. 二期实施记录（2026-10-05）

- 新增 `SUB2API_ADMIN_API_KEY` 配置（`.env.example`、`docker-compose.yml` 已加）。留空时不调用 Sub2API，订单类工单照常提交，订单记为“未校验”，仍按订单号查重。
- `app/orders/sub2api.py` 只开放订单列表和订单详情两个接口。按订单号查询时同时带 `user_id` 过滤，并在 Ops 端再次核对订单号完全一致、`user_id` 一致，Sub2API 的模糊匹配不会误命中其他订单。
- 迁移 `006_ticket_orders.py`：新增 `ticket_orders` 表（用途、订单号、Sub2API 订单 ID、订单快照）。快照只保留金额、币种、状态、类型、支付方式和时间，不含付款人邮箱、支付链接、二维码等。
- 查重规则：同一订单的退款或开票工单，未关闭时不能重复提交；**已解决过的即使关闭了也不能再提交**（三期加入驳回结果后会细化）。充值/支付类允许重复。提交时用 PostgreSQL advisory lock 串行化同一订单，避免并发重复。
- 可退款状态：`COMPLETED / REFUND_REQUESTED / REFUND_FAILED`。可开票状态：`COMPLETED / PARTIALLY_REFUNDED`，且可开票金额大于 0。充值/支付类不限状态。开票的多个订单必须同一币种。
- 订单查询（提交前预览和提交校验共用）按用户每分钟最多 30 次，计数存在后端进程内存里（当前为单进程部署）。
- Sub2API 不可用或 Key 无效：用户看到“订单校验服务暂时不可用”，工单不创建；具体原因写入后端日志，管理员“查询实时状态”时直接显示。
- 前端：建单页“查询订单”预览（开票显示可开票金额和合计）；用户和管理端详情显示关联订单；管理端可查询实时状态，列表新增订单号列、“待退款”“待开票”筛选，搜索支持订单号。
- 验证：后端 79 个测试通过（新增 9 个，使用模拟的 Sub2API）；迁移 `006` 在 PostgreSQL 上升级、降级、再升级通过；在 PostgreSQL 上实测建单和并发锁下的重复拦截；本地用模拟 Sub2API 走通建单前查询、提交开票、管理端筛选和实时状态。

## 8. 三期实施记录（2026-10-05）

- 迁移 `007_ticket_resolution.py`：`tickets.resolution`、`ticket_attachments.kind`（GENERAL / INVOICE_FILE）、`ticket_refund_operations` 表。
- 接口（均为管理员）：`POST /admin/tickets/{id}/refund`、`/refund/sync`、`/refund/manual`、`/reject`、`/invoice`。
- **退款结果以 Sub2API 订单状态为准**：每次退款先在 Ops 记一条操作（处理中）再请求 Sub2API，请求后重新读取订单：`REFUNDED / PARTIALLY_REFUNDED` 记成功；`REFUND_PENDING / REFUNDING` 记“渠道处理中”；请求超时或读不到订单记“结果未知”。处理中和结果未知的操作会挡住新的退款和驳回，必须点“同步结果”确认（渠道处理中时会先调 Sub2API 的退款查询接口）。同一工单的退款请求加行锁串行处理。
- Sub2API 要求确认（余额不足、找不到订阅）时记“需要确认”，面板显示中文说明和“强制执行”按钮，强制执行会按原请求的金额和扣减设置重发，只多带 `force=true`。
- 发出请求前在 Ops 端先校验：退款额度大于 0、最多两位小数、不超过订单当前到账额度，订单状态可退款。永远传明确金额（Sub2API 中 0 表示全额）。退款原因写入“工单号 · 操作人 · 原因”。
- 成功后自动回复用户（原路退回金额按实付折算、扣减的余额或订阅天数），工单改为已解决。“同步结果”也能登记在 Sub2API 后台直接完成的退款（方式记为“从 Sub2API 同步”，扣减余额未知）。
- 未配置 Key 时退款面板改为手动登记（金额、备注）；配置了 Key 时不允许手动登记，统一用同步。
- 开票登记：发票号码（字母、数字、-，4 到 40 位）、开票日期（不晚于今天）、金额（订单都已校验时不超过可开票金额）、PDF 附件（面板内可直接上传）、勾选“已发送至收票邮箱”。登记后附件标记为发票，用户详情页可下载。
- 驳回（退款和开票）：原因回复给用户，工单改为已解决；**被驳回的申请不再阻止同一订单重新申请**（二期的查重规则已据此调整）。
- 约束：表单类退款、开票工单不登记结果不能改为已解决（旧版工单不受影响）；登记过结果或发起过退款的工单不能改分类。用户接口不返回退款操作记录和处理人。
- 管理端事件时间线改为中文名称。
- 验证：后端 91 个测试通过（新增 12 个，覆盖成功、需确认、渠道处理中、超时、渠道未开启退款、网关失败回滚、金额与状态校验、驳回后重新申请、状态和分类约束、外部退款同步、手动登记、开票校验）；迁移 `007` 在 PostgreSQL 上升级、降级、再升级通过，并在 PostgreSQL 上实测工单内退款；本地用模拟 Sub2API 走通需确认后强制退款、驳回、开票登记和用户端查看结果。
- 未覆盖：真实支付宝退款。上线后请用一笔小额订单实测“部分退款 → 到账 → 余额扣减 → 工单自动回复”。
