# 使用手册随 Ops Extension 部署

使用手册源码现位于 `frontend/manual/`。它是一套可直接编辑的静态 HTML、CSS、JavaScript、图片和下载文件，无需单独安装依赖、构建服务或启动文档容器。

`frontend/Dockerfile` 在构建 Ops 前端镜像时，将手册复制到 `/usr/share/nginx/html/docs/`。同一 Nginx 容器提供 `/ext/app/` 和 `/docs/`，主项目 Sub2API 与 Ops Extension 仍分别更新。手册随 Ops 前端发布和回滚，不再执行独立的文档发布。

## 后台手册配置（不用改代码）

经常变动的内容已经做成可配置，管理员在 Ops 后台“手册配置”页面（`/ext/app/admin/manual`）修改，**保存即生效，不需要重新构建或部署**。手册页面最多缓存 1 分钟。

| 分组 | 可配置内容 |
| --- | --- |
| 基本信息 | 站点地址（自动生成三个客户端的接口地址）、客服 QQ、手册更新时间、手册顶部公告 |
| 推荐模型 | Claude Code / Codex / WorkBuddy 各自的可用模型、排除模型、推荐顺序，用“模型 ID + 通配符”填写 |
| Claude 角色 | Fable / Opus / Sonnet / Haiku / 子代理的匹配顺序，找不到时用主模型 |
| 安装与客户端 | npm 镜像和备用源、Node.js 镜像与版本、npm 包名、Codex 微软商店 ID、WorkBuddy winget ID 和官网、WorkBuddy 模型参数 |
| CC Switch 下载 | 版本号、Windows 安装包（填地址或上传到文件库）、GitHub 发布页 |

- **工作方式**：手册加载时请求 `GET /ext/api/v1/public/manual-config`。接口不可用或返回的值不合格时，自动使用随手册打包的 `frontend/manual/assets/manual-config.default.json`，页面照常可用。
- **安全**：这些值会写进用户电脑上运行的安装/配置脚本。后端保存时按白名单格式严格校验，手册生成脚本前、脚本运行时各再校验一次。
- **版本**：每次保存生成一个新版本，记录修改人和说明；可以对比任意版本与当前配置的差异，“恢复到此版本”会生成新版本，旧版本都保留。
- **文件库**：上传的安装包存放在 MinIO（`manual/` 前缀），通过 `/ext/api/v1/public/manual-files/{编号}/{文件名}` 公开下载，单个最大 100 MB。如果入口是 nginx，`/ext/api/` 的 `client_max_body_size` 需要不小于 110m（见 `nginx/ext.conf.example`）。
- **默认值**：首次访问时用 `backend/app/manual/default_config.json` 写入版本 1。它必须和手册里的 `manual-config.default.json` 完全一致，后端测试会检查；修改默认值时两份一起改。

## 日常维护

页面结构、文字说明和截图仍在代码里。直接编辑以下文件，再按现有 Ops Extension 发布流程构建前端镜像：

| 内容 | 文件 |
| --- | --- |
| 手册首页（选择路线、账号准备、用量、排错、客服） | `frontend/manual/index.html` |
| 新手路线（一键安装、一键配置、恢复） | `frontend/manual/quick.html`、`assets/quick.js`、`assets/quick-config-core.js` |
| 进阶路线（CC Switch 导入与手动配置、WorkBuddy） | `frontend/manual/cc-switch.html`、`assets/ccswitch.js`、`assets/ccswitch-setup-core.js` |
| 一键安装脚本模板（页面按勾选改写 `HUIMA_TOOLS` 行，并写入后台配置的安装来源） | `frontend/manual/assets/downloads/huima-install.cmd` |
| 读取后台配置、填入页面 | `frontend/manual/assets/manual-config.js`、`assets/manual-config-core.js` |
| 手册逻辑测试 | `frontend/tests/manual/`，运行 `npm run test:manual` |
| 旧页面跳转（claude-code / codex / workbuddy / setup） | `frontend/manual/` 下同名 HTML，仅含跳转 |
| 品牌标识与图标 | `frontend/manual/assets/brand/` |
| 样式、导航行为 | `frontend/manual/assets/docs.css`、`assets/docs.js` |
| 截图与 CC Switch 安装包 | `frontend/manual/assets/screenshots/`、`assets/downloads/` |

前端镜像的构建上下文仍为 `frontend/`，不需要更换 Compose 的 `build.context`。一般 Compose 部署中，前端发布命令是：

```bash
docker compose build ops-frontend
docker compose up -d --no-deps ops-frontend
```

Windows 下载脚本必须保留 CRLF 换行。仓库 `.gitattributes` 将 `*.cmd` 指定为 `text eol=crlf`，用于 Git 检出与发布归档；网页生成 CMD 下载时也统一为 CRLF。发布验收除校验文件内容外，应确认 CMD 无单独的 LF 换行，并在 Windows 验证启动入口，避免出现本地可运行、线上下载后命令被截断或窗口闪退的问题。

生产环境应继续使用该环境现有的 Compose 文件、镜像标签及发布覆盖文件，不能用仓库示例 Compose 覆盖生产配置。手册改动也需要重新构建前端镜像；只重启容器不会更新静态文件。手册与前端在同一镜像内，回滚前端镜像会同时回滚手册。

## 入口代理的一次性调整

对本机 Caddy 入口，将原来的文档静态文件块替换为：

```caddyfile
redir /docs /docs/ 308

handle /docs/* {
    reverse_proxy 127.0.0.1:8088
}
```

使用 `handle` 保留 `/docs/` 前缀，不能继续使用会剥离前缀的 `handle_path`。本服务器 Caddy 使用宿主网络，所以 `127.0.0.1:8088` 指向 Ops 前端映射端口；其他 Docker 网络部署应根据网络实际情况改用容器服务名。原有 Sub2API `/docs/batch-image` 路由继续放在文档通配路由之前。

完整示例见 `nginx/manual.caddy.example`；Nginx 入口示例见 `nginx/ext.conf.example`。文档的 CSP、缓存策略和其他响应头由 Ops 前端 Nginx 提供，原有文档目录可以保留作迁移备份，但不再作为线上文件源。

```bash
curl -I https://api.tysy.top/docs
curl -I https://api.tysy.top/docs/
curl -I https://api.tysy.top/docs/quick.html
```

```bash

sudo sh -c 'cat "$1/Caddyfile.before" > /opt/sub2api-caddy/Caddyfile' sh "$record"

sudo docker exec sub2api-caddy caddy reload --config /etc/caddy/Caddyfile --adapter caddyfile

sudo docker compose -f /opt/ops-extension/docker-compose.prod.yml \
  -f /opt/ops-release-config/docker-compose.release.json up -d --no-deps --no-build ops-frontend
sudo cp "$record/last-code-release.before" /opt/ops-release-config/last-code-release
```

Caddyfile 采用原地写入，保证 Docker 文件绑定挂载继续读取同一文件。原文档发布目录和旧前端镜像已保留。回滚仅恢复线上部署，本地下载的源码及镜像打包配置仍可保留用于后续修订。

`frontend/manual/` 与配套配置、说明随 Git 仓库统一维护；以后从 GitHub 拉取目标提交并构建 Ops 前端镜像即可同步发布手册。原来的 `deploy_docs.py` 和文档目录软链接属于旧发布流程，迁移完成后不再用于日常更新。
